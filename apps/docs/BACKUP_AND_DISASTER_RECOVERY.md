# Backup, Restore & Disaster Recovery Procedures

## 1. Overview
This document outlines the Disaster Recovery (DR) procedures, Backup strategies, and Restore operations for the Marketplace Platform. The system relies on automated scripts ensuring data durability and rapid recovery in the event of hardware failures, accidental deletions, or ransomware incidents.

## 2. Backup Strategy

### Development
- **Mechanism**: Local file-system backup.
- **Frequency**: On-demand triggered by developers.
- **Retention**: 7 days.
- **Location**: `backups/development/`
- **Command**: `npm run db:backup`

### Staging
- **Mechanism**: Scheduled chron job (local to staging server).
- **Frequency**: Daily.
- **Retention**: 14 days.
- **Location**: `backups/staging/`
- **Command**: `npm run db:backup` (Set `NODE_ENV=staging`)

### Production
- **Mechanism**: Automated chron job pushing to S3-compatible cloud storage.
- **Frequency**: Daily / Hourly depending on load.
- **Retention**: 
  - Daily: 30 days.
  - Weekly: 12 weeks.
  - Monthly: 12 months.
- **Location**: `backups/production/` -> AWS S3.
- **Security**: AES-256 Encryption at rest and TLS 1.3 in transit.
- **Command**: `npm run db:backup` (Set `NODE_ENV=production`)

## 3. Restore Operations

**Warning:** Restoring a database drops current data matching the backup archive.

### Command Usage
```bash
npm run db:restore <backup_file_name>
```
*Example:* `npm run db:restore backup-production-2023-10-01.gz`

### Safety Protocols
- **Development / Staging**: Requires standard `y/N` prompt confirmation.
- **Production**: Requires explicit text confirmation (`RESTORE-PRODUCTION`) to prevent accidental overwrites.

## 4. Disaster Recovery (DR) Scenarios

### Scenario A: Accidental Data Deletion (Single Entity)
1. Do **NOT** run a full restore immediately.
2. Rely on **Application-Level Soft Delete**.
3. A privileged Admin can invoke the `restore(userId)` method on the soft-deleted model (e.g. `Product`, `User`, `Store`).
4. Result: Data instantly recovered without system downtime.

### Scenario B: Database Corruption or Malicious Overwrite
1. Isolate the compromised database container/cluster.
2. Identify the last known good backup from S3.
3. Fetch the backup to the recovery server.
4. Run `npm run db:restore <backup_file_name>` locally.
5. Verify application integrity.
6. Swap production connection strings to the recovered cluster.

### Scenario C: Complete Cloud Region Failure
1. Provision new database cluster in secondary region.
2. Pull latest replicated backup from S3 multi-region bucket.
3. Run `mongorestore` targeting the new URI.
4. Update Route53/DNS configurations to point to the fallback region.

## 5. Recovery Objectives
- **RTO (Recovery Time Objective):** 2 Hours (Maximum acceptable downtime).
- **RPO (Recovery Point Objective):** 24 Hours (Maximum acceptable data loss window, to be reduced to 1 hr as real-time streaming scales).

## 6. Testing & Validation Drills
- **Development**: Monthly drills.
- **Staging**: Bi-weekly automated restore validations against CI/CD.
- **Production**: Quarterly full disaster recovery failover exercises. 
- Logging: All backup/restore actions are piped through standard `logger.ts` for monitoring via Datadog/ELK.
